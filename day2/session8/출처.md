# 입력 영상과 처리 조건

원본 영상: https://github.com/jonathanfoster/ball-tracking/blob/master/ball_tracking_example.mp4

7교시와 같은 녹색 공 영상을 사용합니다. 1152×640 원본을 576×320으로 축소한 뒤 원본 20~140번 프레임을 포함했습니다. 총 121프레임, 재생 기준 30FPS입니다. 프레임 번호는 0부터 셉니다.

HSV 범위는 H 35~85, S 80~255, V 60~255입니다. Contour 면적 80 pixel² 이상을 후보로 두고 Bounding box 중심을 대표 좌표로 사용합니다. 연결 허용 거리는 35 pixel이며 최근 30개 위치를 표시합니다. 처음 후보가 하나일 때 시작하고, 누락·거리 초과·동률이면 이전 위치와 경로를 지웁니다.

576×320과 288×160의 처리 크기를 비교합니다. 축소에는 INTER_AREA를 사용하며, 후보 좌표를 크기 비율로 나누고 면적을 크기 비율의 제곱으로 나누어 원래 기준으로 환산합니다. 영상 읽기와 결과 그리기는 두 조건 모두 576×320입니다. 축소 비용은 후보 검출 구간에 포함합니다.

강의자료 PDF 11페이지와 노트북의 확대는 클립 80번(원본 100번)의 x227:357, y35:165 영역입니다. 두 조건의 같은 영역을 같은 크기로 표시합니다. 마스크를 원래 크기로 표시할 때는 INTER_NEAREST를 사용합니다.

시간은 perf_counter로 측정합니다. 전체 시간은 첫 프레임 읽기 직전부터 마지막 정상 완료 프레임의 기록까지입니다. 파일 열기, 표시 창 준비, 마지막 읽기 실패, 해제, 결과 보고서·영상 저장은 측정 밖입니다. 각 조건의 준비 실행 한 번 뒤 세 번 기록합니다. 프로그램 FPS는 완료 수/전체 시간이며, 개별 프레임 FPS를 평균하지 않습니다.

분석 시간은 후보 검출과 위치 연결의 합입니다. 화면 표시를 켜면 imshow와 waitKey(1)를 함께 실행합니다. waitKey(1)은 정확히 1ms에 처리를 완료하거나 특정 FPS를 보장하는 설정이 아닙니다. 이번 측정은 촬영부터 실제 모니터 표시 완료까지의 지연이 아닙니다.

Python 시간 측정: https://docs.python.org/3/library/time.html#time.perf_counter
OpenCV 화면 표시·키 입력 대기: https://docs.opencv.org/4.13.0/d7/dfc/group__highgui.html
OpenCV 영상 속성: https://docs.opencv.org/4.13.0/d4/d15/group__videoio__flags__base.html

코드에서 사용하는 timing_helpers.py와 practice_views.py는 함께 제공하는 보조 함수 파일입니다. OpenCV 내장 함수 이름이 아닙니다. 강사 PC의 처리 시간과 학생 PC의 처리 시간이 일치해야 하는 것은 아닙니다.

## 입력 영상과 처리 조건

입력은 7교시의 normal.avi다. 1152×640 원본의 0부터 세는 프레임 20~140을 포함하며, 총 121프레임이다. 576×320, 재생 기준 30FPS, FFV1 형식의 입력을 모든 비교 조건에서 동일하게 읽는다. 사진에 추가한 노이즈나 밝기 변환은 없다.

색상 후보는 OpenCV의 8비트 HSV 범위 (35, 80, 60)~(85, 255, 255)로 구한다. RETR_EXTERNAL과 CHAIN_APPROX_SIMPLE로 외곽 Contour를 구하고, 576×320 좌표 기준으로 환산한 Contour 면적이 80pixel² 이상인 후보를 남긴다. 별도 필터나 Morphology는 적용하지 않는다.

후보 위치는 boundingRect의 박스 중심이며 실수 좌표를 유지한다. 이전 위치에서 가장 가까운 후보를 고르고, 허용 거리 35pixel 이하일 때 연결한다. 최소 거리 동률, 후보 누락 또는 거리 초과 시 이전 위치와 경로를 지운다. 이전 위치가 없으면 후보가 하나일 때 추적을 시작한다. 경로는 최근 30개 위치를 이은 선이다.

두 처리 크기는 576×320과 288×160이다. 작은 크기는 INTER_AREA로 가로·세로를 각각 1/2로 축소한다. 좌표는 각 축의 비율로 나누고 Contour 면적은 두 축 비율의 곱으로 나누어 원래 좌표 기준으로 환산한다. 환산 후 동일한 면적·거리 기준을 적용한다. 입력 읽기와 결과 그리기는 모든 조건에서 576×320이며, 결과 표시는 수행 여부만 바꾼다.

## 측정 범위

전체 반복 시간은 첫 프레임을 읽기 직전부터 마지막 정상 프레임의 결과 기록과 처리 완료까지다. 읽기, 검출, 연결, 그리기, 설정된 화면 표시·키 입력 대기, 반복 관리가 포함된다.

파일 열기, GUI 창 준비, 준비 실행, 마지막 파일 끝 확인을 위한 실패한 읽기, 창과 파일 닫기, 결과 영상 저장, 측정표 출력은 제외한다. 영상 저장은 측정 후 별도로 수행한다.

|구간|포함하는 처리|
|---|---|
|읽기|VideoCapture.read 호출|
|검출|해당 조건에서의 축소, BGR→HSV 변환, 색상 마스크, Contour와 박스 계산, 면적·좌표 환산|
|연결|후보 선택, 거리 판정, 이전 위치와 경로 갱신|
|그리기|후보 박스·후보 번호·선택 위치·경로 표시|
|표시·대기|imshow와 waitKey(1). 표시 제외 조건에서는 모두 수행하지 않음|
|반복 관리|기록, 구간 시간 집계, 이름 붙인 구간 밖의 시계 호출과 반복 관리|

N은 처리를 정상 완료한 프레임 수, T는 전체 반복 시간(초)이다. 처리 FPS는 N/T이며 평균 프레임당 시간은 1000T/N(ms)이다. 구간별 평균은 해당 구간의 누적 시간을 N으로 나누고 ms로 환산한다. 프레임별 순간 FPS의 산술평균을 사용하지 않는다.

표시 여부를 바꿔도 결과 그리기는 그대로 수행한다. waitKey(1)은 전체 반복 시간을 1ms로 고정하는 설정이 아니다. 표시 포함·제외의 시간 차이를 순수한 imshow 실행 비용으로 해석하지 않는다. 같은 처리를 수행해도 다른 구간의 경과 시간 역시 달라질 수 있다.

## 결과 이미지와 집계

1·5·10·11페이지의 대표 장면은 원본 프레임 100, 포함된 클립의 프레임 80이다. 두 번호 모두 0부터 센다. 11페이지는 원래 크기의 x 227~356, y 35~164 영역을 동일하게 표시한다. 배열 자르기로는 x[227:357], y[35:165]이며 130×130 영역이다.

작은 마스크는 최근접 보간으로 576×320에 맞춘 뒤 같은 영역을 확대한다. 결과 그리기는 원래 크기의 영상에 수행한다. 노란 박스는 후보, 노란 번호는 해당 프레임 안의 후보 순서, 빨간 원은 계산으로 선택된 위치, 파란 선은 저장한 최근 위치를 이은 경로다. 후보 번호를 지속적인 물체 ID로 사용하지 않는다.

대표 프레임의 중심 좌표는 전체 크기에서 (292.0, 99.5), 작은 크기에서 원래 좌표로 환산하면 (292.0, 99.0)이다. 환산 Contour 면적은 각각 5535.5, 5378.0pixel²이다. 두 조건의 위치와 경계가 완전히 같다고 설명하지 않는다.

모든 9회 실행에서 121프레임을 정상 완료했다. 각 실행은 후보가 있는 프레임 121개, 선택된 위치가 있는 프레임 121개, 추적 시작 1회, 연결 120회다. 후보 프레임 수는 후보가 하나 이상 있던 프레임 수이며, 연결 수는 이전 위치와 연결한 횟수다. 정답 라벨과 대조한 인식 정확도를 뜻하지 않는다.

## 설명용 숫자와 해석 범위

- 3페이지: 102.340초와 102.352초의 차이 0.012초, 즉 12ms는 시간 계산을 위한 설명용 숫자다.
- 4페이지: 120프레임, 2초, 60FPS, 평균 약 16.7ms는 계산 예시다. 실제 입력의 121프레임과 구분한다.
- 12페이지: 일정한 30FPS 입력과 20ms 또는 45ms의 순차 처리를 가정한다. 입력 시점은 0, 약 33.3, 약 66.7ms다. 20ms 처리의 종료 시점은 약 20, 53.3, 86.7ms이고, 45ms 처리의 종료 시점은 45, 90, 135ms다. 모두 순서대로 처리할 때의 예시이며 실제 카메라의 버퍼나 프레임 폐기 정책을 측정한 것이 아니다.
- 13페이지: 12페이지와 별개인 설명용 예시다. A의 결과는 각 촬영 시점에서 40ms 뒤, B는 140ms 뒤에 나온다. 두 경우 모두 결과 간격은 약 33.3ms다. 40ms와 140ms는 계산 시간이 아니라 촬영부터 결과까지의 지연이다.

이번 실행에서는 카메라의 실제 촬영 주기, 화면의 실제 표시 완료 시각, 촬영부터 표시까지의 지연, 정답과 비교한 인식 정확도를 측정하지 않았다. 처리 FPS만으로 이러한 값을 추정하지 않는다.

## 강의 운영

14페이지 총 60분이며 설명, 코드 빈칸 작성, 실행과 결과 비교를 포함한다. 페이지별 배정은 3, 4, 4, 4, 4, 6, 4, 5, 4, 5, 5, 4, 4, 4분이다. 학생이 작성하는 두 빈칸은 perf_counter 호출과 n / elapsed이며, 답은 강의자료 PDF 3·4페이지에서 확인한다. 준비 코드, 검출과 연결, 반복 측정, 좌표 환산과 결과 출력은 완성된 형태로 제공한다.
